## 1. Tech Stack

| Technology | Purpose |
|------------|---------|
| Next.js App Router | Server Actions (primary API), Route Handlers (`/api/*`, `/auth/callback`) |
| TypeScript (strict) | Typed actions, services, DTOs |
| Zod | Validate every incoming payload (`features/*/dto`) |
| `@supabase/ssr` | Cookie-based server client (`shared/lib/supabase/server.ts`) |
| `@supabase/supabase-js` | Typed `Database` client, admin client for streak writes |
| Supabase PostgreSQL + RLS | Data + final security guard (see DATABASE.md) |
| Vitest | Unit tests for pure logic (trap engine, mastery rules) |

## 2. System Overview

- **Style**: Monolith. Next.js App Router is the whole backend; Supabase provides auth, the database and RLS
- **Question Engine**: deterministic, pure TypeScript run on the server (`questionEngine` + `notePatterns` + `trapEngine`, Section 7); no DB, no network, no LaTeX

```
Browser (React 19)
  │
  ├──► Server Components ─┐
  ├──► Server Actions ────┼──► features/*/services ──┬──► Supabase Auth
  └──► Route Handlers ────┘                          └──► PostgreSQL + RLS
                │
                └──► shared/lib/trapEngine.ts (pure: no DB, no network)
```

## 4. Feature Anatomy

One folder per feature holds both its server and UI code. Only the folders a feature needs are created.

```
features/[feature]/
├── actions/      # SERVER · 'use server' entry points: validate → auth → service → ActionResult
├── services/     # SERVER · Supabase queries (import 'server-only'); the only layer touching the DB
├── dto/          # SHARED · Zod schemas (DrillSubmissionDto, CreateDeckDto)
├── lib/          # SHARED · Pure helpers (progress/lib/masteryRules.ts)
├── types/        # SHARED · Domain types + UI view models
├── components/   # CLIENT · UI (see frontend/PROJECT-RULES.md)
├── hooks/        # CLIENT · UI state, calls actions
├── __tests__/    # Vitest
├── index.ts      # Public, client-safe: actions, components, hooks, types
├── server.ts     # Public, server-only: services for other features' server code
└── context.md    # Owned tables, exports, allowed dependencies
```

- `index.ts` never re-exports `services/` (it would pull `server-only` code into the client bundle)

## 6. Request Flow

```
Client (form / hook)
  │  submitDrillResult({ itemId, seed, tag })
  ▼
Server Action ('use server')
  │  1. DrillSubmissionDto.safeParse(input) ── fail ──► { success: false, error: VALIDATION_FAILED }
  │  2. supabase.auth.getUser()            ── none ──► { success: false, error: AUTH_UNAUTHORIZED }
  ▼
Feature Service: recordDrillResult(supabase, user.id, dto)
  │  select / upsert (user JWT attached)
  ▼
PostgreSQL (RLS enforced) ── denied ──► empty rows / policy error
  │  rows
  ▼
ActionResult<T> ──► Client receives { success, data, meta } or { success, error }
```

| Step | Responsibility | Failure code |
|------|----------------|--------------|
| Zod validation | Shape, lengths, UUIDs, plain-text check | `VALIDATION_FAILED` |
| Auth check | Resolve user from cookie session | `AUTH_UNAUTHORIZED` |
| Service query | Business logic + Supabase call | `*_NOT_FOUND`, `INTERNAL_ERROR` (full list: API_SPEC.md §5) |
| RLS | Final safety net at DB level | Empty rows or a policy error |

## 7. Question Engine (plain text)

Two pure, deterministic layers in `shared/lib/` (no `Math.random`, no `Date`, no DB, no network, no LaTeX; guarded by tests):

| Module | Job |
|--------|-----|
| `notePatterns.ts` | Reads mindmap notes: implicit subject, `Key: Value` / `Key - Value` / `Key = Value`, definition markers, cloze targets, short phrases, `[author marks]` |
| `questionEngine.ts` | Builds one multiple-choice question per note and seed, from the note and its deck (`prepareDeck` → `buildQuestion`), in 8 conceptual trap types; `trapTypes` (the eligible pool), `typedSeed` / `seedTrapType` |
| `conceptPatterns.ts` | Statement shapes for types 5, 7, 8: `parseConditional` (A does B when C, When C A does B, Khi / Nếu …), `parseScenario` (…, e.g. … / Ví dụ: …), `conceptOf`, `isFormula` + `formulaVariants` |
| `trapEngine.ts` | One-change variants: `antonymVariants` (type 1), `siblingSwapVariants` (type 4), `operatorVariants`, `oppositeVariants`; the older `generateTraps` (7a) |

**Zero drop**: every note gets a question. Notes are fragments in a mindmap, so the engine never requires a full sentence.

```
DeckNote = { id, nodeId, statement, path /* root titles, top → own root */, ancestry /* their ids */, rules }
prepareDeck(notes) ─► analyse every note once (sorted: DB order never matters)
buildQuestion(deck, noteId, seed) ─► { kind, trapType (1–8 | null), context (breadcrumb), prompt, instruction, choices (2–4, A–D), correctTag }
trapTypes(deck, noteId) ─► the trap types the note is eligible for · typedSeed(type, base) = "t{type}{base}"
```

Quality rules for every type: no misspellings, phonetic lookalikes, double negatives or surface tricks; every wrong answer is a well-formed statement or expression that differs in meaning, mechanism or mathematics (tested: every word of every choice comes from the tree, the opposite / negation dictionaries or a mutated index).

| Type | Kind | When the note supports it | Prompt → choices |
|------|------|---------------------------|------------------|
| 1 Semantic antonym | `antonym` | An opposite keyword (dictionary `OPPOSITE_PAIRS`, the author's `trap_rules.swaps`); last resort, with `negate` and no negation already in the note, the negated predicate. A variant with two negations is never made | "Which statement is true?" → the proposition + variants |
| 2 Cloze | `cloze`, `recall-right`, `recall-left` | A cloze target with a wrong option (`[author marks]` make cloze the only kind); a `Key: Value` / definition pair with other pairs in the deck | The note with one target blanked → the term + other notes' terms (numbers: plausible wrong numbers) · `Ty thể: ____` → values · `____: …` → keys |
| 3 Concept mapping | `category`, `recognize` | The note doesn't name its own root, and other unrelated roots exist · (short phrases) items filed under other roots | The statement → "Which topic does this belong to?" → its root + unrelated roots (never an ancestor or descendant; the badge shows only the parent) · "Which note belongs under “Root”?" |
| 4 Sibling swap | `sibling` | A subject swap with a sibling statement (same root; else a sibling root under the same parent) | "Which statement is true?" → the proposition + the claim about sibling concepts |
| 5 Scenario | `scenario` | The note gives a worked example (`…, e.g. …`, `for example`, `such as`, `Ví dụ: …`, `chẳng hạn`) that doesn't name the concept | "Scenario: <example>." → "Which concept is demonstrated?" → the claim's subject (`conceptOf`) or the root + other concepts / topics |
| 6 Least likely | `least-likely` | ≥ 3 notes under the root and one under an unrelated root | "Which of the following is LEAST LIKELY a characteristic of “Root”?" → 3 notes of the root + 1 alien (the answer) |
| 7 Condition | `conditional-outcome`, `conditional-condition` | A conditional / causal statement (`when`, `if`, `whenever`, `once`, `because`, `khi`, `nếu`, `hễ`, `vì`; condition first or last) | "When C: what happens?" → the main clause + near misses (one opposite word, a number moved to an adjacent value) and other conditionals' outcomes · "A does B ____." → "when C" + near-miss conditions and sibling mechanisms' conditions |
| 8 Formula | `formula` | An equation, ratio between symbols, indexed variable (D0, D_1), time step (t + 1) or compounding factor (1 + r) with a mutation | "Which formula is correct?" → the formula + index shifts (D0 ↔ D1), (1 + r) → r, sign swaps (r − g → r + g), × ↔ ÷, fraction inverted (a / b → b / a) |
| fallback | `recognize`, then `exact` | No type fits (`exact`: alone in its deck; outside the 8 types, `trapType: null`) | The same recognition · "Which is exactly your note?" → copies with two words swapped / one dropped |

- **Contextual inheritance**: a predicate-only note ("compiles down to clean JavaScript", "sản sinh ATP", "is a superset of…": it starts with a predicate word, or it's a lower-case fragment with no subject) borrows its own root's title as subject, so the proposition is "TypeScript compiles down to clean JavaScript". Clauses (`khi`, `when`…), pairs and notes with their own subject are left alone. Every question carries its breadcrumb (`context`), shown as a badge.
- **Choosing**: which kinds a note supports doesn't depend on the seed. A typed seed (`t{1–8}…`, `typedSeed`) asks that type when the note supports it; a plain seed (Daily Rush) picks a type with equal odds, then one of its questions; the seed also shuffles the choices.
- **Scheduling** (`drill/lib/trapSchedule.ts` `scheduleTrapTypes`, used by `buildDrillSession` for practice and tournament rounds): each question gets the least-used type its note is eligible for (≈ 12.5 % each when all 8 are eligible; ties by the session seed) and never a type used by either of the last 2 questions; when the next note can only repeat one, one of the next 4 goes first; a repeat only when nothing else can go. The type travels in the question's seed, so grading rebuilds that exact question (the seed still passes the `[0-9a-z]{1,16}` DTO check).
- **Distractors**: closest notes first (shared breadcrumb); only from the note's own top-level subject when it has any there (fewer, plausible choices beat an obvious odd one out); never the answer, never text already in the note, never a title from the note's own breadcrumb, never a root title as a cloze filler.
- **The only undrillable note**: one with no two distinct words or letters and nothing else in its deck (a lone "aaa"). `decks/lib/drillable.ts` `isDrillable` = `isNoteDrillable` (askable even alone): the editor's ✅ / 💧.
- **Grading**: the client gets `kind`, `context`, `prompt`, `instruction`, `choices` and `seed`, never `correctTag`. `submitDrillResult` / `checkDrillAnswer` / `submitTournamentAnswer` rebuild the question from the seed and the **whole deck** (`decks/server` `findDrillItem` returns `deckItems`, the same rows `listDrillItems` gives the session), so a one-branch round grades against the same context (`drill/__tests__/questionConsistency.test.ts`). No self-graded cards: mastery and 🪙 come only from a server-checked pick.

### 7a. Trap mutations (`trapEngine.ts`, the `statement` kind)

```typescript
export type TrapRules = { swaps?: { from: string; to: string }[]; negate?: boolean }
export type DrillTag = 'A' | 'B' | 'C' | 'D'          // traps use A–C
export type DrillChoice = { tag: DrillTag; text: string }
export type TrapResult =
  | { ok: true; choices: DrillChoice[]; correctTag: DrillTag }   // 2 or 3 choices
  | { ok: false; reason: 'INSUFFICIENT_MUTATIONS' }
// siblings = the propositions of the other notes in the same root
export function generateTraps(correctStmt: string, rules: TrapRules, seed: string, siblings?: string[]): TrapResult
```

```
proposition + trap_rules + seed + sibling propositions (same root)
  ▼
Tier 1 · context      sibling concept swaps  ("Ty thể | sản sinh ATP" + "Ribosome | …" → "Ribosome sản sinh ATP")
                      then trap_rules.swaps (legacy / seeded items)
Tier 2 · built-in     opposite pairs (tăng ↔ giảm, trước ↔ sau), then operators (* ↔ /, + ↔ -)
Tier 3 · negation     only if negate (is ↔ is not, là ↔ không phải là)
  ▼
Dedupe across tiers; drop the original and any sibling's own statement (it is true)
  ├── 0 candidates ──► INSUFFICIENT_MUTATIONS (the question engine then uses another kind)
  ▼
Pick up to 2 traps tier by tier (seeded shuffle inside each tier) ──► 2 or 3 choices
```

| Source | Match rule | Example |
|--------|------------|---------|
| Sibling concept swap | Subject = text before the first predicate marker (`PREDICATE_MARKERS`: sản sinh, tổng hợp, là, chứa, produces, is…). 1–6 words, no comma, not a clause (`CLAUSE_STARTERS`: khi, nếu, when, if…). Otherwise no swap | `Ty thể sản sinh ATP` → `Ribosome sản sinh ATP` |
| `trap_rules.swaps` | Case-insensitive whole word/phrase | `ATP` → `DNA` |
| Opposite pairs | Both directions, longest phrase first (`trapDictionary.ts`: tăng/giảm, trước/sau, tạo ra/tiêu thụ, inhale/exhale, produce/consume…) | `Nhiệt độ tăng` → `Nhiệt độ giảm` |
| Operators | Only between operands (`3 * 4`, `a+b`); tight `-` and `/` need digits on both sides, so hyphens in words and units (`km/h`) are skipped | `F = m * a` → `F = m / a` |
| Negations | Only when `trap_rules.negate` is true; both directions, longest first | `Ty thể là bào quan` → `Ty thể không phải là bào quan` |

- **One mutation per distractor**: each trap differs from the original in exactly one place (a sibling swap replaces only the subject)
- **Unicode-safe boundaries**: `(?<!\p{L})…(?!\p{L})` with the `u` flag; `\b` breaks on Vietnamese diacritics
- **Deterministic**: `seed = hash(itemId + sessionId)`; the engines only use `seededRandom(seed)`. Inputs are NFC-normalized, deduped and sorted inside, so database order doesn't matter
- **Known limits**: a sibling swap can be accidentally true when two concepts share a property ("Ty thể" and "Lục lạp" both make ATP); an exact copy of a sibling statement is always dropped. If the deck changes mid-round, an in-flight answer is graded against the new deck

## 8. Shared vs Feature Scope

| Shared (`src/shared/`) | Feature (`src/features/*`) |
|------------------------|----------------------------|
| Supabase client factories (`server`, `browser`, `admin`) | Query services (`getDeckTree`, `recordDrillResult`) |
| `trapEngine.ts`, `trapDictionary.ts`, `seededRandom` | Action validators (`CreateDeckDto`, `DrillSubmissionDto`) |
| `ActionResult<T>`, `ErrorCode`, `database.types.ts` | Domain entities (`DeckTree`, `MasteryLevel`), `masteryRules.ts` |

**Rule of thumb**: code goes to `shared/` only if it has no feature knowledge and is used by 2+ features (or is infrastructure).

## 9. Key Design Decisions

| Decision | Why |
|----------|-----|
| Server Actions over REST | Type-safe calls, no API layer to maintain for a solo dev |
| One folder per feature (server + UI) | One place per domain; `index.ts` / `server.ts` keep the bundle split safe |
| RLS as the final guard | A bug in a service can't leak private decks |
| Seeded determinism | Reproducible drills, testable engine, grading without storing sessions |
| Streak via admin client | `practice_days` is not client-writable, so days can't be faked (DATABASE.md) |
| Progress only, no answer history | An answer updates the item's level and review time in place and marks the day (one row per player per day). No per-answer rows, timings or picks: less to store, nothing to leak |
